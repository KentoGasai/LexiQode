# Cursor parity record

What we set out to reproduce, what we measured, and where we stand. Every number
below was produced by a script in this repository or by an REA MCP call against
the installed build, and the raw output is kept next to this file.

## Method

| tool | what it gave us |
|---|---|
| `scripts/measure_cursor_surface.py` | text-level surface of the patched workbench bundles and of every `cursor-*` extension |
| `scripts/rea_mcp.py` + REA MCP server | structural analysis of the agent extensions, Electron fuse state, artifact inventories |
| `docs/cursor/cursor-ui-surface.json` | raw measurement output, regenerated by the script above |

Nothing is executed. The bundles are parsed as text and as inert syntax.

## What Cursor actually ships

Cursor's agent is **not** in its extensions. The extension manifests are almost
empty - 20 `cursor-*` directories, two of which declare a single command each -
while the real UI lives in patched workbench bundles:

| bundle | bytes | distinct `cursor.*` ids | agent tool names |
|---|---|---|---|
| `workbench.glass.main.js` | 49,206,434 | 1145 | 7 |
| `workbench.desktop.main.js` | 41,367,735 | 1031 | 6 |
| `workbench.anysphere-ui-automations.js` | 8,897,316 | 9 | 0 |
| `out/main.js` (main process) | 2,471,851 | 77 | 0 |
| `out/bootstrap-fork.js` | 19,283 | 0 | 0 |

`AnySphere` is Cursor's legal entity, which is why its automation bundle carries
that name.

## Matrix

Status is deliberately blunt: *done* means covered by the core and its tests,
*pending* means specified but not written, *not planned* means we chose a
different mechanism on purpose.

| capability | Cursor | LexiQode |
|---|---|---|
| agent chat over a workspace | yes | **done** (core), UI pending |
| model-agnostic endpoint | no - vendor service | **done** - any OpenAI-compatible URL, key and model id |
| read / search code (`read_file`, `grep`, `glob`, `list_dir`) | yes | **done** |
| edit files (`edit_file`, `write_file`) | yes | **done** |
| run builds, tests and linters | yes | **done** (`run_command`) |
| command approval before execution | yes | **done** (`docs/protocol.md` §7) |
| refusal is fed back to the model | yes | **done** - a denial is a tool result, not an abort |
| workspace confinement | yes | **done** - enforced by `ToolContext.resolve` |
| project rules file | yes (`fetch_rules`) | **done** - `LEXIQODE.md`, `AGENTS.md`, `.lexiqode/rules.md` |
| conversation restored per folder | yes | **done** (session store) |
| diff review before applying | yes | pending - extension |
| inline edit (`Ctrl+K`) | yes | pending - extension |
| tab autocomplete | yes | pending - extension |
| modes: agent / ask / plan / spec / debug / multitask / triage / project | yes | pending - core already emits the events a mode UI needs |
| MCP client | yes (`cursor-mcp`) | pending - the transport has its own module slot |
| web search tool | yes (`web_search`) | not planned - pulls in a search vendor; `run_command` can call a user's own tool |
| embedding codebase search | yes (`codebase_search`) | not planned initially - `grep` plus `glob` cover the common case without an index to maintain |
| lint reading tool | yes (`read_lints`) | not planned - the project's own command reports the same thing, in its own format |
| delete-file tool | yes (`delete_file`) | not planned - deletion goes through `run_command` with an approval, so it is visible and reversible via git |

## Deliberate differences

* **No vendor service.** The core has no notion of an account, a plan or a
  quota. It knows a base URL, a key and a model id.
* **Three tool families, one policy.** Cursor surfaces many tools; we group them
  into `read`, `write` and `command` so the approval decision is one clear
  question instead of a per-tool list to memorise.
* **Protocol, not in-process API.** The editor talks to the core over HTTP and
  SSE (`docs/protocol.md`). That makes the agent testable without an editor and
  replaceable without touching the UI.
* **Loopback plus a per-process token.** The API never listens publicly and the
  token is never written to disk.

## Next probes

Recorded so the next investigation starts where this one stopped:

1. `cursor-ai` and `cursor-retrieval` bundles: how the retrieval index is built
   and stored, to decide whether an incremental text index is worth adding.
2. The `composer` id space in the glass bundle: the diff/review flow, which is
   the largest remaining UI gap.
3. Electron fuse state of `Cursor.exe` (REA `inspect_electron_fuses`) to see how
   the packaged app constrains its own main process.
4. `cursor-mcp` patch against `@modelcontextprotocol/sdk` 1.25.1: which upstream
   behaviour Cursor had to change, and whether our own MCP client must handle it.
